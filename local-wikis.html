Running NetHackWiki locally for fun and profit

Unpublished

Recent events have me thinking about how impermanent things are on the web. One site goes out of business, another gets overrun by fascists and the users leave, someone leaves a university and with them is gone /~alex13/uploads/2010.pdf that everyone linked to for some reason. A lot of things that are meaningful to me have been lost this way.

So I’ve been trying to do a better job about archiving things that I care about, and do more things local-first — or, failing that, homelab-first.

I’ve also become more familiar with Nix and NixOS, I’ve really appreciated the way they take knowledge I have about software and reify it into a form I can share. I don’t have the greatest memory. It’s comforting to feel like I’ll always be able to read a shell.nix to figure out what I was using for a project, or look at a years-old part of my config and not have to question which parts of it were auto-generated and which reflected decisions I made somewhere along the way. It has made it easier to get over the irritation that comes with trying new software. It’s not an exaggeration that declarative program & service configuration is an accessibility aid to me, and I’m certainly not alone in this.

So, let’s get some Nix experience by doing a local archiving project that’s a little more involved than just downloading PDFs.

The task

I play a little NetHack, but as a noob, I’m constantly looking at nethackwiki.com as I play. This effectively makes NetHack a game for which I need an internet connection, but it feels a little silly that my experience with the game is gated behind just accessing some text documents online. So, wouldn’t it be nice if it wasn’t?

Warning: the rest of this article will have a few spoilers for NetHack.

Step 1. Getting a local copy of the wiki data

The wiki makes its articles available in the form of MediaWiki XML dumps.

The challenge is getting these XML dumps into a readable form. The wiki says:

You can install mediawiki locally, but it’s quite a bother

and recommends a couple possible “offline Wikimedia XML reader” programs. The issue is that MediaWiki markup isn’t one standard format, it’s very extensible through plugins, and the NetHackWiki takes full advantage of that extensibility. For example, the article for Medusa’s Island includes a fancy level map, where interesting characters are turned into hyperlinks:

We could try to find or build an offline reader that duplicates every plugin installed on the NetHack wiki, but that feels like we’d be fighting an uphill battle. So let’s bite the bullet and run a MediaWiki instance locally.

Step 2. Prerequisite system stuff

My ideal user experience is that you can just run a few commands and get a MediaWiki server running on a particular port.

NixOS has a MediaWiki module (source code, wiki article), but I don’t want users to have to rebuild their system just to run this server. MediaWiki isn’t the most lightweight thing, so we only want to run it some of the time.

So instead, we’re going to run it in a container, and start that container with Podman.

This forum post gives us an example configuration to start with:

default.nix:

(import <nixpkgs/nixos> {
  configuration = {
    imports = [
      ./podman-base.nix
      ./mediawiki.nix
    ];
  };
}).system

podman-base.nix:

{ lib, modulesPath, ... }:
{
  imports = [ "${modulesPath}/profiles/minimal.nix" ];

  services.journald.console = "/dev/console";
  boot.specialFileSystems = lib.mkForce {};
  boot.isContainer = true;
  boot.postBootCommands = "mkdir /run/wrappers";

  networking.hostName = ""; # seems to be auto-generated anyway
  users.mutableUsers = false;
  services.getty.autologinUser = "root";
  users.users.root.hashedPassword = "";
  users.users.mediawiki.hashedPassword = "";

  services.logrotate.enable = lib.mkForce true;

  networking.dhcpcd.enable = false;
  systemd.oomd.enable = false;
  services.nscd.enableNsncd = false;
  networking.firewall.enable = false;
  services.openssh.startWhenNeeded = false;
  services.lvm.enable = false;
  system.stateVersion = "24.11";
}

This is enough to get a booting Podman container.

nix-build container-image

mkdir -p root # empty dir for container FS

podman run                                  \
    -ti --rm                                \
    -v '/nix/store:/nix/store:ro'           \
    --systemd=always --env container=podman \
    -p 8228:8228                            \
    --rootfs root:O                         \
    $(readlink result)/init

# -ti --rm       Get Podman into a mode that feels a bit like a Nix shell -
#                the container starts, gives us a shell, and deletes the
#                container when we use `shutdown now` from the shell
#
# -v ...         Mount the Nix store read-only
#
# --systemd=...  Enable systemd and do some configuration
#
# -p 8228:8228   Forward container port 8228 → host port 8228
#
# --rootfs ...   Indicate that we have an "exploded container"
#
# $(...)/init    Path to the binary to run (use `readlink` to get a Nix
#                store path readable from the container)

Step 3. Reducing nethackwiki_current.xml

The raw download from the wiki nethackwiki_current.xml is over 36,000 pages and ends up ~185 MB decompressed.

This doesn’t seem like too much, but the script to import the XML dump into a database (ImportDump.php) doesn’t go very fast. It averages 10-12 pages per second on my machine, so with all 36,000 pages it would take almost an hour to process the whole thing.

However, it’s possible to filter out almost 2/3 of pages, reducing import time significantly. Pages I cut were:

  • User and user talk pages.
  • I kept main talk pages. There are about 1,000 of them, so they would be nice to prune, but some have useful information.
  • Game source code — one could keep a separate local copy of this, maybe even redirecting Source: links automatically, but I haven’t done that.
  • Chinese (/zh-CN) and Korean (/ko) translated pages.
  • Pages tagged as specific to a variant.
  • File: pages, which are useless since the associated files weren’t downloaded anyway. (Including assets would have increased the download size significantly, and most assets are tiles which I don’t need since I play with text graphics, but you could keep them.)

The resulting file nethackwiki_current_reduced.xml is 166 MB and 12,338 pages. Note that we haven’t actually reduced the file size much, but we have made importing dramatically faster since it seems like load time is dominated by constant overhead per DB operation and doesn’t scale much with the size of inserted pages.

Step 4. MediaWiki configuration

Now it’s time to set up the NixOS MediaWiki module. MediaWiki really just consists of a pile of PHP scripts, and is configurable by a choice of web servers (apache vs. nginx) and databases (MySQL vs. Postgres). Unfortunately I ran into some permissions issues with MySQL: it doesn’t seem to like the reduced level of privilege that results from running as root inside a container which is not itself running as root. Sadly this means we have to set aside our dreams of bringing back LAMP in 2025, and while we’re at it, I’ll go with nginx too since that’s what I’m more familiar with.

mediawiki.nix:

let
  port = 8228; # chosen arbitrarily
in
{
  services.mediawiki = {
    enable = true;
    name = "NetHackWiki";
    database.type = "postgres";
    webserver = "nginx";
    nginx.hostName = "localhost:${toString port}";
  };
}

There’s an unfortunate interaction between nginx and mediawiki that comes in the hostName field. I don’t think the NixOS module author really expected the server to run on a port other than 80, but MediaWiki expects the hostname to include the port, whereas nginx expects it not to.

We can fix this by touching the generated nginx config and telling it explicitly which port it needs to listen on.

{
  services.nginx = {
    enable = true;
    recommendedGzipSettings = true;
    recommendedOptimisation = true;
    recommendedProxySettings = true;
    recommendedTlsSettings = true;
    virtualHosts."localhost:${toString port}" = {
      serverName = "localhost-${toString port}";
      listen = [ { addr = "0.0.0.0"; inherit port; } ];
    };
  };
}

Step 5. Security

I’ve pulled this into its own section so I have a chance to warn against doing anything unwise.

The configuration I’m presenting in this article assumes you only care about accessing a local, read-only view of the wiki, and that the port is not open to the Internet.

I cannot make any guarantees about what a malicious actor would be able to do to the host machine given access to the wiki.

Got it? Cool. So we don’t have to worry about the password then.

{
  services.mediawiki.passwordFile = pkgs.writeText "password" "<arbitrary>";
}

Step 6. Extensions

The wiki needs some extensions to work. The full list is at Special:Version, and some of them (category navigation, page editing & moderation tools) are not necessary for our read-only view of the wiki, but there are others which are important and easy to enable since they’re bundled with MediaWiki by default.

{
  services.mediawiki.extensions = {
    ImageMap = null;
    Cite = null;
    Math = null;
    Scribunto = null;
    Poem = null;
    ParserFunctions = null;
  };
}

Step 7. Importing the dump

While running the container I’ve run into some situations where I’ve wanted to run some of the MediaWiki maintenance scripts. The NixOS module includes a derivation that creates binaries for some of these scripts, but it doesn’t include all the ones I need, and it seems like in recent versions of MediaWiki they want you to use them through a wrapper script called run.php. So we’ll ignore the built-in scripts and create our own simple wrapper around run.php instead.

let
  # find the paths to PHP and the generated config file
  mediawiki       = config.services.mediawiki.finalPackage;
  php             = config.services.phpfpm.pools.mediawiki.phpPackage;
  mediawikiConfig = config.services.phpfpm.pools.mediawiki.phpEnv.MEDIAWIKI_CONFIG;
  maintenance = pkgs.writeShellScriptBin "maintenance.php" ''
    export MEDIAWIKI_CONFIG="${mediawikiConfig}"
    ${php}/bin/php ${mediawiki}/share/mediawiki/maintenance/run.php "$@"
  '';
in
{
  environment.systemPackages = [ maintenance ];

  # expose some paths in the container to make it easier to find things
  environment.variables = {
    "mediawiki"        = "${mediawiki}";
    "mediawiki_config" = "${mediawikiConfig}";
  };
}

Finally, we create a systemd service which runs on boot and imports the dump from the file /etc/intake.xml

{
  systemd.services.mediawiki-intake = {
    # target depends on this service so that it gets run on startup
    wantedBy = [ "multi-user.target" ];
    # but it can only be run after mediawiki-init
    after = [ "mediawiki-init.service" ];
    script = ''
      export PATH="${maintenance}/bin"
      maintenance.php nukePage --delete "Main_Page"
      maintenance.php importDump /etc/intake.xml
    '';
    serviceConfig = {
      Type = "oneshot";
      User = "mediawiki";
      Group = config.services.nginx.group;
      PrivateTmp = true;
    };
  };
}

This also requires we change the Podman command to also mount the XML file into /etc:

podman run                                                    \
    -ti --rm                                                  \
    -v '/nix/store:/nix/store:ro'                             \
    -v "$PWD/nethackwiki_current_reduced.xml":/etc/intake.xml \
    --systemd=always --env container=podman                   \
    -p 8228:8228                                              \
    --rootfs root:O                                           \
    $(readlink result)/init

We did it

It takes a while (~15 minutes on my machine) to import all the pages, but it works!

My homelab was $15 from a university and another $15 for the hard drive.
